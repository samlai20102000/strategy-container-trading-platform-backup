# 訊號匯出與盈虧問題分析筆記

**狀態：分析中；未經使用者確認，不修改或發布生產邏輯。**

## 圖片一分區觀察

1. 左側第一列可見「幣種：全部」、「方向：全部」、「策略：全部策略」。
2. 日期範圍可見起點 `01/01/2026 12:00`，終點 `28/07/2026 12:00`，旁有清除日期的 `×` 控制。
3. 中段可見「訊號狀態：全部」、「來源：全部」及「層級：0 ～ 20」。
4. 最右側有獨立的「CSV」下載鍵與「循環報告」鍵；使用者要求把匯出入口移入訊號日誌右上角，並改為先開啟篩選確認流程。
5. 以上是圖片中實際顯示的篩選狀態；尚未判斷前端是否把條件正確傳至後端。

## 圖片二分區觀察

1. 區塊標題為「訊號日誌（人類語言壓縮・技術明細折疊）」並顯示「共 290 筆」。
2. 左側可見「時間」與「策略」欄，列表混合多個策略，包括「20415七彩虹馬丁策略 - 導入」、「KAMA 3K V6.1 高頻掃射 - 導入」與只顯示編號的 `#60007`。
3. 這證明訊號日誌本身不是零資料；CSV 的「總訊號數 0」與畫面「共 290 筆」形成明顯矛盾，需追查是否兩者使用不同查詢、不同時間欄位或不同策略識別值。
4. 中段欄位依序可見「來源、動作、交易對、價格、狀態、盈虧、訊息」。來源均顯示「自動交易」，動作同時包含「賣出」與「平倉」，交易對為 `BTCUSDT`。
5. 多筆 `20415七彩虹馬丁策略 - 導入` 的「平倉」列，價格顯示 `—`、狀態為「已執行」、盈虧顯示 `—`，但訊息欄可見止盈百分比；這是**同一資料列內已知止盈語意、卻缺少結構化盈虧欄位**的直接證據。
6. 對照列中，`KAMA 3K V6.1 高頻掃射 - 導入` 的平倉可顯示 `+2.74 U`，`#60007` 的平倉可顯示 `+0.64 U`。因此不是整個盈虧欄元件失效，而是不同策略／執行路徑寫入的結構化已實現盈虧資料不一致。
7. 最右分區可精確讀到兩筆七彩虹平倉訊息分別為「止盈 ++0.62%」與「止盈 ++0.72%」，兩筆的盈虧欄仍是 `—`；其後兩筆可正常顯示的對照為「`+2.74 U`／止盈 `+2.67%`」與「`+0.64 U`／止盈 `+0.539%`」。
8. 訊息中的百分比只能證明策略曾產生報酬率語意，不能可靠推導實際 USDT 盈虧；要根治必須在成交／平倉時保存交易所成交量、成交均價、方向、費用與已實現盈虧等結構化事實，不能再由自然語言訊息反向解析。

## CSV 原始證據

匯出檔只有 7 行、190 bytes。第一行是 8 欄表頭；其後沒有任何訊號資料列，只有「匯出摘要」。摘要顯示策略「七彩虹線趨勢跟蹤階梯馬丁策略 (全跟)」、幣種 `BTCUSDT`、總訊號數 `0`、已執行 `0`、失敗 `0`。因此這不是欄位值全空，而是**匯出查詢結果為零筆後仍生成摘要檔**。

## 空匯出的程式級根因

1. 首頁訊號日誌查詢在「策略＝全部策略」時，把 `strategyId` 傳為 `undefined`，因此 `signals.list` 會正確查詢全部策略；這與畫面顯示 290 筆一致。
2. 同一頁的 `handleExportCSV` 與 `handleExportCycleReport` 卻把「全部策略」轉成 `strategies[0].id`。策略清單又按 `createdAt DESC` 排序，所以匯出不是「全部」，而是**任意取最新建立的第一個策略**；新增、刪除或重建策略後，匯出目標還會改變。
3. 後端 `strategies.exportData` 強制要求單一 `strategyId`，再以該 ID 分別查詢 trades/signals。它沒有「全部策略」語意，所以前端不可能產生與目前訊號日誌相同的 290 筆資料。
4. 圖片一的幣種與層級篩選完全沒有傳給匯出 API，後端 input 也沒有對應欄位。循環報告更只傳日期，連訊號狀態、來源與方向都忽略。因此畫面篩選、列表查詢與兩種匯出是三套不同契約。
5. 後端在查詢為零筆時仍照常組出表頭與摘要；前端不驗證 `rowCount`，一律下載並提示「CSV 匯出成功」。這是**假成功**，不是單純顯示問題。
6. 使用者提供的檔案正是上述分歧的結果：訊號日誌查的是全部策略，匯出卻只查「七彩虹線趨勢跟蹤階梯馬丁策略 (全跟)」，最後生成零資料列但顯示成功的檔案。

## 盈虧缺值的程式與資料庫根因

1. 訊號日誌前端不計算盈虧，只顯示 `sig.realizedPnl`；其為 `null`、空字串或零時一律顯示 `—`。因此訊息寫有「止盈 +0.54%」不會自動變成 USDT 盈虧，這個行為本身避免了從自然語言猜數字。
2. `db.listSignals` 只會從 trades 左連接 `realizedPnl`：優先 `signals.id = trades.signalId`；只有 trade 的 `signalId IS NULL` 時才容許以雙方相同 `orderId` 後備關聯。任一端缺 signalId/orderId，列表就拿不到盈虧。
3. 圖片所指的真實資料庫列已確認：`2026-07-28 17:32:50`、策略 `20415七彩虹馬丁策略 - 導入`、signal `180001`，訊息明確為「止盈觸發平倉成功…空倉盈虧 +0.54%」，但 signal 的 `orderId` 為 null。進一步查到**同一策略、同一秒的 trade `180001` 已有交易所成交價 `63573.27142857`、成交量 `0.0238` 與 `realizedPnl = 1.56986 USDT`**，卻因 trade.signalId 亦為 null，列表 join 完全找不到它。這證明使用者看到的 `—` 不是沒有實際盈虧，而是已有結構化盈虧被關聯缺陷遮蔽。
4. `riskMonitor.enforceRisk` 的順序是先平倉、先建立 trade，最後才建立 signal；trade 沒有 signalId，signal 又沒有保存平倉 orderId，兩者天然斷鏈。現行程式中的該 createTrade 呼叫亦沒有把 `realizedPnl` 列為強制輸入；資料庫範例雖已有值，仍不能保證新事件與未來策略持續寫入。**本例的直接顯示故障是關聯斷裂；系統性風險則同時包括關聯與 PnL 寫入都未被契約強制。**
5. OKX adapter 的成交明細查詢其實已讀到 `pnl`，但 `OrderResult` 介面沒有 realizedPnl 欄位，呼叫端也只複製 filledPrice/filledSize，導致交易所提供的 PnL 被程式丟棄。Bybit 的 placeOrder 只回傳 orderId；另有 closed-PnL API，但目前未與平倉單統一關聯。
6. 靜態掃描全部 31 個 `createTrade` 正式寫入點：20 個為 reduce-only 平倉；其中 4 個缺 signalId、6 個缺 realizedPnl、2 個連共用成交真相 helper 都未使用。缺口分布於手動平倉、緊急全平倉、通用 executor close、通用 engine close、每日虧損平倉與 generic risk monitor，不是單一 20415 策略的局部錯誤。
7. V3.5、V5.0、V6.1 專用監控已有正確對照模式：先建立 signal 取得 signalId，再建立 trade 並保存 `tradeFillRecordFields` 與 realizedPnl。這證明 UI 能正常顯示；真正問題是各策略／控制路徑各自重寫平倉持久化，沒有強制共用契約。

## 初步結論

兩個問題具有相同架構根因：**列表、匯出、成交、訊號與績效各自擁有不一致的資料契約**。若只在 20415 或匯出按鍵內補條件，未來新增策略仍會重現。根治方向必須是：一個共用 signal/trade 查詢契約、一個共用平倉成交記錄服務、一個可表達資料來源與完整度的 PnL 真相模型，以及由後端產生並驗證的匯出工作流。

## 全策略交易真相與盈虧契約草案

本次不應再針對 20415、V3.5、V5.0、V6.1 等策略逐一補洞，而要把所有自動策略、Webhook、風控止盈／止損、每日虧損、手動平倉與緊急全部平倉統一導向同一個 `recordTradeExecution`／`recordCloseExecution` 服務。未來策略只能呼叫這個共用服務，不得直接各自 `createTrade`、`createSignal`。

| 契約層 | 強制規則 | 缺值處理 |
|---|---|---|
| 事件識別 | 每次交易建立唯一 `executionId`；每一張成交單只對應一個 signal 與至少一筆 trade | 使用資料庫唯一約束避免重複寫入 |
| 建立順序 | 先建立 signal，再下單；成交後以同一交易更新 signal 並建立關聯 trade | 任何一步失敗皆保留可重試狀態，不可產生「已執行但無成交事實」 |
| 關聯鍵 | `trade.signalId` 必填；`signal.orderId` 與 `trade.orderId` 同步；交易所成交 ID 另存 | 不再以策略名稱、訊息文字或模糊時間作為日常 join |
| 成交真相 | 保存請求價／量、實際成交均價／量、成交時間、交易所與資料來源 | 未取得成交回報時標記 `pending_reconciliation`，不可假填 0 |
| PnL 真相 | 優先保存交易所已結算毛利、手續費、資金費、淨利與幣別 | 交易所暫未回傳時，可依入場批次與實際成交計算，但必須標為 `calculated_from_fills` |
| 品質標記 | `pnlSource`、`dataQuality`、`reconciledAt`、`reconciliationError` 結構化保存 | UI 顯示「待對帳／估算／交易所確認」，不可一律顯示破折號 |
| 跨策略覆蓋 | 策略只輸出標準化交易意圖；記錄、PnL、費用與匯出由平台層處理 | 未來新增策略若繞過契約，型別檢查與測試必須失敗 |

PnL 來源優先序建議為：`exchange_settlement`（交易所已結算淨額）→ `exchange_fill_calculation`（交易所成交價量加費用）→ `position_snapshot_calculation`（平倉前持倉快照加成交）→ `unavailable`。只有第一級可標示為「交易所確認」；其餘均需附品質說明。訊息中的 `+0.54%` 只可作為舊資料回填候選與顯示後備，不能冒充 USDT 真值。

對於交易所回傳延遲的成交，建議在下單請求內先做一次短時重查；仍未完整時寫入 `pending_reconciliation`，再由平台的週期性 HTTP 對帳每分鐘批次處理未完成項目。此工作必須具備冪等鍵、兩分鐘內完成、只查待補資料，且不得使用程序內計時器。

### 現有資料回填原則

第一階段可精準回填雙向關聯：相同使用者、策略、orderId 的 signal/trade 直接連結；orderId 缺失時，只有在相同策略、相同動作／方向、同一秒且候選唯一時才可自動連結。像 signal `180001` 與 trade `180001` 的同策略同秒唯一配對可回填，並立即恢復 `1.56986 USDT` 顯示。多候選或證據不足者不可猜測，應標記 `legacy_unresolved` 供審計。

## 訊號日誌整合匯出互動草案

現有篩選卡右側的「CSV」與「循環報告」兩個按鍵應移除，改在「訊號日誌」卡片標題右上角放置單一 **「生成交易報告」** 按鍵。按鍵不直接下載，而是依序完成「選擇條件 → 後端預檢 → 使用者確認 → 生成檔案」，與使用者要求一致。

| 步驟 | 畫面與行為 | 強制防護 |
|---|---|---|
| 1. 選擇範圍 | 預設「沿用目前訊號日誌條件」，亦可切換「自訂」或「全部歷史」 | 清楚顯示時區與開始／結束時間 |
| 2. 設定篩選 | 交易所、交易帳戶、幣種、策略多選、方向、動作、訊號狀態、來源、觸發原因、層級、PnL 品質 | 「全部策略」必須是後端真正的無 strategyId／多策略查詢，不能再取 `strategies[0]` |
| 3. 選擇內容 | 交易明細、循環績效、完整審計；可選 CSV 或 Excel 工作簿 | 明確顯示每種格式包含的工作表／欄位 |
| 4. 預檢 | 後端先回傳符合筆數、日期範圍、已執行／失敗／跳過、平倉數、PnL 完整率與待對帳數 | 若 0 筆，禁用生成並列出造成零筆的條件；不得下載空檔或提示成功 |
| 5. 確認 | 顯示「將匯出 N 筆、M 筆有交易所確認 PnL、K 筆待對帳」及實際篩選摘要 | 使用者按「確認生成」後才建立檔案 |
| 6. 生成 | 後端依同一查詢契約分頁讀取全部資料、生成檔案並回傳下載 | 不可靜默截斷 10,000 筆；超大檔需顯示總筆數與生成狀態 |

### 建議篩選條件

為保持日常操作簡潔，彈窗第一層只顯示日期、策略、幣種、動作、狀態與來源；「進階篩選」再展開交易所／帳戶、方向、觸發原因、馬丁層級、PnL 來源與資料品質。狀態必須包含 `received`、`executed`、`failed`、`rejected`、`skipped`，避免診斷時遺漏被跳過訊號。

### 建議輸出內容

建議預設輸出 **Excel 工作簿**，另保留「單一 CSV 明細」作輕量選項。Excel 不把摘要混在資料列底部，而是拆成下列工作表，使人可閱讀、程式亦可再分析。

| 工作表 | 每列粒度 | 主要欄位 |
|---|---|---|
| `交易明細` | 每一筆 signal／execution；多成交時可展開 fill | signalId、tradeId、executionId、策略 ID／名稱／版本、交易所、帳戶遮罩、幣種、方向、動作、來源、狀態、觸發原因、signal／order／fill 時間、orderId、成交 ID、請求價量、成交均價／量、名義金額、reduceOnly、層級、毛利、手續費、資金費、淨利、PnL%、PnL 幣別、PnL 來源、資料品質、訊息與錯誤 |
| `交易循環` | 每次完整開倉至平倉循環，按幣種與持倉方向獨立配對 | cycleId、策略、方向、開倉／平倉時間、持倉時間、加倉層數、加權入場價、實際平倉價、總量、毛利、費用、淨利、回報率、平倉原因、完整度 |
| `摘要` | 本次匯出一組統計 | 實際篩選、總訊號、成交、失敗、跳過、平倉、勝負、總毛利、總費用、淨利、勝率、profit factor、平均盈虧、最大單筆盈虧、平均持倉時間、PnL 完整率 |
| `資料品質` | 每一筆缺失／估算／待對帳項 | recordId、缺失欄位、品質狀態、PnL 來源、最後對帳時間、錯誤與建議處理 |

CSV 選項則只輸出規格化的 `交易明細`，摘要改放在下載前確認畫面與獨立 metadata，不再把 `# 匯出摘要` 混入 CSV 明細列。所有文字欄位使用標準 CSV escaping，不可只把逗號替換成空格；時間同時輸出 UTC ISO 8601 與使用者本地時區欄位。
