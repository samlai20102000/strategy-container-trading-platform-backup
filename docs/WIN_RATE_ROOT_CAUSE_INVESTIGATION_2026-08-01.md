# 儀表板勝率 43.9% 根因調查與修復報告

> **狀態：已完成。** 本報告記錄 2026-08-01 對儀表板總勝率、訊號日誌、交易報告與底層成交資料的完整重建結果。修正已通過真實資料稽核、完整測試、production build、桌面畫面與零交易副作用驗收。

## 結論摘要

原畫面顯示的 **43.9%（90 勝／115 負）並不代表 115 筆實際虧損**。當時的 205 筆可解析 `realizedPnl` row 中，實際分布是 **90 筆正數、1 筆負數、114 筆零**；舊程式把 114 筆開倉／加倉的零 PnL 全部放進勝率分母，並把「不是勝場」統稱為負場。

修正後，勝率只使用已成交、`reduceOnly = true`、具有可解析淨已實現 PnL 並完成穩定識別去重的平倉結果。真實資料重算結果為 **90 勝、1 負、24 持平**；持平不進分母，因此正式勝率是：

> **90 ÷（90 + 1）= 98.9%**

| 指標 | 舊畫面口徑 | 修正後口徑 |
| --- | ---: | ---: |
| 勝場 | 90 | 90 |
| 實際負場 | 被混在 115「負」之中 | 1 |
| 開／加倉零 PnL | 114 筆誤列為負 | 排除並獨立揭示 |
| 已確認持平平倉 | 併入「負」 | 24，獨立顯示 |
| 勝率分母 | 205 | 91 |
| 總勝率 | 43.9% | **98.9%** |

## 43.9% 的原始資料來源

在使用者截圖所對應的資料快照中，儀表板只納入當時仍存在的四個策略，其中策略 `150008` 尚無交易。其餘三個策略的 raw `realizedPnl` 分布如下：

| 策略 ID | 有 `realizedPnl` 的 row | 正數 | 負數 | 零 | 舊畫面計算 |
| --- | ---: | ---: | ---: | ---: | --- |
| 60008 | 93 | 51 | 1 | 41 | 51 勝／42 負 |
| 90003 | 91 | 30 | 0 | 61 | 30 勝／61 負 |
| 120011 | 21 | 9 | 0 | 12 | 9 勝／12 負 |
| **合計** | **205** | **90** | **1** | **114** | **90 勝／115 負 = 43.9%** |

上述 **114 筆零 PnL 全部是 `reduceOnly = false` 的開倉／加倉 row**。它們不是已完成的虧損交易，也不應進入任何平倉勝率分母。

系統在調查期間仍持續寫入交易資料，因此最終稽核快照若套用舊公式會變成 90 勝／120 非勝、42.9%；這是即時資料自然增加所致。新公式在同一最終快照仍穩定得到 **90 勝／1 負／24 持平、98.9%**，根因與修正結論不受資料漂移影響。

## 根因鏈

問題不是訊號日誌把多筆止盈寫錯，而是儀表板對 raw trade row 的解讀過度寬鬆，並在前端再次使用近似值聚合。

| 層級 | 修正前行為 | 影響 |
| --- | --- | --- |
| 後端績效摘要 | 只要 `realizedPnl` 可解析為數字就列入；沒有檢查 `reduceOnly`、`status`、成交／訂單去重或資料品質 | 開／加倉保存的 `0` 被誤當已平倉結果 |
| 勝負分類 | `PnL > 0` 算勝，其餘全部成為非勝／負 | 零 PnL 被誤標成虧損 |
| 前端總計 | 從已四捨五入的策略勝率乘回交易數，再 `Math.round` 反推勝場 | 產生第二層可避免的聚合誤差 |
| 訊號日誌 | 使用 `pnlState`、`reduceOnly` 與對帳狀態 | 與儀表板不是同一統計來源，造成觀感矛盾 |
| 交易報告 | 原有自己的摘要聚合路徑 | 未來可能與儀表板再次漂移 |

## 已落地的唯一勝率口徑

正式摘要函式現在嚴格執行以下規則：

1. 只接受 `reduceOnly === true` 的平倉 row。
2. 只接受 `status === "filled"` 的已成交結果。
3. PnL 優先使用 `netRealizedPnl`，舊資料才回退 `realizedPnl`。
4. 以 `exchangeTradeId → orderId → executionId → tradeId` 的優先序建立穩定去重鍵。
5. 同鍵重複 row 優先保留有 net PnL、已確認對帳、交易所確認及 fill ID 的可信版本；同可信度時取較新 row。
6. `PnL > 0` 為勝、`PnL < 0` 為負、`PnL = 0` 為持平。
7. 勝率分母只使用 `wins + losses`；持平獨立顯示，不是負場，也不進分母。
8. 開倉、加倉、非成交、pending、unresolved、缺 PnL 與重複 row 全部排除，並分項揭示資料品質數量。

> **勝率定義：** `wins / (wins + losses) × 100%`。若沒有有方向結果，勝率為 0，而不是由零 PnL 或未解資料補足分母。

## 真實資料重算結果

最終快照共有 288 筆目前策略的 raw trade rows；正式口徑辨識出 115 筆已知平倉結果，其中 91 筆有方向、24 筆持平。

| 策略 ID | 策略 | 勝 | 負 | 持平 | 勝率分母 | 勝率 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 60008 | KAMA 3K V6.1 高頻掃射 | 51 | 1 | 0 | 52 | 98.1% |
| 90003 | 20415 七彩虹馬丁策略 | 30 | 0 | 24 | 30 | 100.0% |
| 120011 | V4.0 KAMA+3K 動態馬丁 | 9 | 0 | 0 | 9 | 100.0% |
| 150008 | 七彩虹線趨勢跟蹤階梯馬丁 | 0 | 0 | 0 | 0 | 0.0% |
| **合計** |  | **90** | **1** | **24** | **91** | **98.9%** |

24 筆持平全部來自策略 `90003`，且資料品質為 `exchange_confirmed`、對帳狀態為 `confirmed`；它們是可信的零 PnL 平倉結果，因此應保留為持平，而不是刪除或列為負場。

| 稽核維度 | 全期間 | 近 30 日 | 近 7 日 |
| --- | ---: | ---: | ---: |
| 已知平倉 | 115 | 115 | 115 |
| 有方向結果 | 91 | 91 | 91 |
| 勝／負／持平 | 90／1／24 | 90／1／24 | 90／1／24 |
| 修正後勝率 | 98.9% | 98.9% | 98.9% |
| 逐策略儀表板＝交易報告 | 是 | 是 | 是 |

三個範圍數值相同，是因目前仍存在策略的相關資料都位於近 7 日範圍內；重點是時間過濾後仍逐策略通過相同一致性斷言。

## 訊號日誌與 Bar-Lock 核對

策略 `90003` 有 48 筆 Bar-Lock／skipped 訊號，`skippedSignalsWithTrade = 0`。這些跳過訊號沒有交易 row，並不是原 115「負」的來源。訊號日誌中的開倉 `0.00 USDT / unknown`、平倉「未解」及 Bar-Lock「已跳過／不適用」均保留其原始資料品質語義，不會被績效摘要誤算成負場。

桌面畫面展開各策略明細後，四個現存策略依序顯示 `0/0/0`、`9/0/0`、`30/0/24`、`51/1/0`，逐列加總與總卡的 `90/1/24` 完全一致。

## 為何不強制以 cycleId 合併成一場

既有 `cycleId` 歷史契約並不適合直接作主要勝率分母。V6.1 策略 `60008` 的同一 `cycleId` 會交錯多次 entry／close，一個 cycle 可包含 15 個平倉成交；部分歷史 close size 與 entry size 也使用不同正規化尺度。

若把整個 `cycleId` 強制縮成一場，反而會把多筆獨立、已由交易所確認的平倉結果錯誤合併。此次因此採用 fill／order／execution／trade 的穩定識別；`cycleId` 繼續作生命週期與報告分組維度，待未來所有策略完成資料契約遷移後再評估是否提供另一種「週期勝率」。

## 最終判定

使用者觀察到的矛盾成立：訊號日誌中的近期已實現止盈多為正，但總勝率卻被顯示為 43.9%。根因是 **開／加倉零 PnL 被錯放進平倉勝率分母，而不是存在 115 筆真實虧損**。

修正後，儀表板、策略明細與交易報告均以同一正式函式計算，畫面直接使用後端整數勝／負／持平，不再反推。依目前可稽核資料，正確總勝率為 **98.9%（90 勝／1 負，另有 24 持平）**。
