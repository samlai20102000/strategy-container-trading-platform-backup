# 全策略實盤部署倉位最終覆寫修復與驗收報告

**作者：Manus AI**  
**日期：2026-07-29**  
**影響範圍：策略交易、快照導入、策略建立／編輯、策略卡片回讀、所有實盤執行管線**

## 一、執行結論

本次問題已由「針對七彩虹線策略的個別修補」提升為**全系統共用部署倉位契約**。現在回測／快照中的 `Base_Lot_Size` 僅代表研究配置與表單預填建議；使用者在建立或編輯策略時最後確認的「實盤部署倉位」才是策略實例的正式執行值。系統的固定優先序為：

> **本次使用者提交的實盤部署值 > 已持久化的策略實例部署值。快照或策略專用配置不得參與最終部署值決策。**

此規則由不接受 `strategy config` 或 `snapshot config` 的共用函式強制執行，因此不是依靠策略名稱白名單，也不只涵蓋目前的七彩虹線、20415、KAMA V3.5、V5.0、V6.1、V7.0；未來新增而尚未命名的策略同樣必須經過相同契約。[1]

| 使用情境 | 快照／回測倉位 | 使用者最終部署值 | 正式持久化與實盤執行值 |
|---|---:|---:|---:|
| 截圖所示七彩虹線導入 | 100 USDT | 500 USDT | **500 USDT** |
| 編輯既有策略，只改數值 | 既有策略配置可仍為 100 | 500，沿用既有單位 | **500 + 既有合法單位** |
| 未知未來策略 | 任意研究值 | 使用者提交值 | **使用者提交值** |
| 重新套用快照到既有策略 | 快照可更新策略邏輯參數 | 未再次變更 | **保留既有實盤部署值** |

## 二、圖片所揭示的問題

使用者提供的畫面中，「七彩虹線趨勢跟蹤階梯馬丁策略」由快照導入時，快照原始倉位為 **100 USDT**；部署表單已將「實盤部署倉位」改為 **500 USDT**，且介面明確表示可獨立覆寫。然而建立後的策略卡片仍顯示 **100.00000000 USDT**。這證明錯誤不是輸入框沒有接收 500，而是伺服器在建立策略時又把快照內的 `Base_Lot_Size=100` 寫回策略實例頂層部署欄位。[10]

根因共有四條舊路徑：一般策略建立、策略更新、從回測快照建立新策略，以及把快照套用到既有策略。這些路徑曾各自處理倉位，部分策略分支更把策略專用配置放在使用者提交值之前，造成相同問題可能在其他策略或未來新策略再次出現。[10]

| 舊問題 | 失敗機制 | 本次根治方式 |
|---|---|---|
| 建立策略後 500 變回 100 | 專用配置 `Base_Lot_Size` 覆蓋表單值 | 建立入口只以共用部署契約產生正式值 |
| 編輯策略後再次被覆蓋 | 更新分支重新從專用配置抽取倉位 | 編輯入口以本次提交值或既有頂層值決策 |
| 快照導入忽略部署覆寫 | 快照研究值被直接當成策略實例值 | 快照只負責邏輯配置；部署值獨立持久化 |
| 套用快照改壞既有實盤值 | 快照套用同步改寫頂層倉位欄位 | 套用快照不再改寫策略實例部署值 |

## 三、統一契約與資料模型

共用模組 `deploymentPosition.ts` 現在是全系統唯一的部署倉位決策點。它先嚴格驗證數值必須大於零且有限，單位只能是 `usdt` 或 `quantity`；再以「使用者提交值優先、既有頂層值次之」完成決策。該函式刻意沒有策略配置或快照配置參數，從型別與函式介面上阻止日後有人再次把 `Base_Lot_Size` 放回優先序。[1]

正式值會同步寫入三個欄位：`positionSize`、`positionMode` 與 `positionSizeObject`。讀取時以頂層欄位為正式來源；只有舊策略缺少或損壞頂層資料時，才逐欄回退舊物件，避免歷史資料突然失效。[1]

| 欄位 | 角色 | 寫入規則 |
|---|---|---|
| `positionSize` | 正式部署數值 | 一律寫入標準化後的使用者最終值 |
| `positionMode` | 正式部署單位 | 僅允許 `usdt`／`quantity` |
| `positionSizeObject` | 數值與單位的同步物件 | 與前兩欄同時寫入，防止欄位分叉 |
| 快照 `Base_Lot_Size` | 回測／策略研究配置 | 保留原值，不作正式部署來源 |

## 四、全流程修復範圍

策略建立、策略編輯以及快照建立新策略都已改用 `finalizeDeploymentPosition` 與 `deploymentPositionColumns`；從快照建立時仍鎖定快照的策略引擎身份，但倉位由使用者最後提交的 `positionSize`／`positionMode` 獨立決定。[4] 策略列表與卡片回讀則統一解析正式頂層部署值，避免畫面再次從策略配置顯示 100。[1] [5]

實盤執行前，系統會建立「本次執行有效配置」：數值型 `Base_Lot_Size` 策略使用數字覆寫，20415 類物件型策略使用 `{ value, mode }` 覆寫；兩者都不修改快照原始物件。這讓舊策略維持原本期待的配置形狀，同時保證實際下單取得策略實例的最終部署值。[1]

| 流程關卡 | 修復後行為 | 防回歸屬性 |
|---|---|---|
| 部署表單 | 顯示可編輯的最終實盤倉位及單位，並標示快照值只作來源參考 | 使用者能在提交前明確確認 |
| 一般建立 | 僅從部署欄位建立正式值 | 不再讀取專用配置作優先值 |
| 策略編輯 | 提交欄位優先；缺少欄位才沿用現有正式值 | 部分編輯不會觸發快照回填 |
| 快照導入新策略 | 引擎與原始配置來自快照，部署值來自部署表單 | 研究配置與執行配置解耦 |
| 套用快照至既有策略 | 更新策略邏輯配置，但保留策略實例正式部署值 | 不會因重新套用快照回到 100 |
| 策略卡片 | 讀取頂層正式值與單位 | 顯示內容與資料庫一致 |
| 實盤下單 | 以正式值產生本次執行配置，再換算交易數量 | 快照值不會在執行階段復活 |

## 五、500 USDT 實際證據鏈

唯讀資料庫驗收已找到一個由快照導入的現有策略實例，其 `positionSize=500`、`positionMode=usdt`，且 `positionSizeObject={"value":500,"mode":"usdt"}` 三欄一致。這證明 500 USDT 不只停留在前端或測試函式，而已能持久化到正式策略資料列。

| 資料列 | 讀取結果 |
|---|---|
| 策略 ID | `120011` |
| 策略名稱 | `V4.0 KAMA+3K 動態馬丁策略（百分比控倉） - 導入` |
| 策略引擎 | `20415_KAMA_MARTIN_V35` |
| `positionSize` | `500` |
| `positionMode` | `usdt` |
| `positionSizeObject` | `{ "value": 500, "mode": "usdt" }` |

決策層回歸測試進一步使用 BTC 價格 `50,000 USDT` 與最終部署 `500 USDT`，確認 V3.5 策略產生的實際委託數量為 `0.01 BTC`，即 `500 ÷ 50,000`，而不是依快照的 100 USDT 產生 `0.002 BTC`。[8]

## 六、跨策略與未來策略防回歸

部署契約測試採表格方式同時涵蓋 `RAINBOW_TREND_LADDER_V1`、`strategy_20415`、`20415_KAMA_MARTIN_V35`、V5.0、V6.1、V7.0，以及刻意不存在於目前系統的 `FUTURE_ENGINE_V99`。每個案例都斷言最後提交 500 USDT 後，三個持久化欄位必須同步為 500 USDT。[2]

另一組快照隔離測試則同時檢查七彩虹線與未知未來策略：快照原始物件繼續保留 100 USDT，正式部署欄位獨立保存 500 USDT，本次執行有效配置才在不修改原物件的前提下使用 500 USDT。這正面覆蓋了本次截圖中的失敗情境，亦證明修復不依賴既有策略清單。[3]

| 測試層 | 關鍵斷言 | 結果 |
|---|---|---|
| 嚴格輸入驗證 | 拒絕零、負數、NaN、Infinity、非法單位 | 通過 |
| 優先序 | 500 USDT 覆蓋既有／預填 100 USDT | 通過 |
| 持久化 | 三個正式欄位同步保存 500／usdt | 通過 |
| 快照隔離 | 快照仍為 100，執行有效值為 500 | 通過 |
| 舊資料相容 | 頂層缺失時安全回退舊物件 | 通過 |
| 未來策略 | `FUTURE_ENGINE_V99` 走相同契約 | 通過 |
| 決策層換算 | 500 USDT @ 50,000 = 0.01 BTC | 通過 |

## 八、視覺驗收限制與判定

本輪自動預覽通道曾對 `/strategies` 與 `/snapshots` 顯示空白根節點；公開入口模組同時回傳 `429 PROXY_RATE_LIMITED`，而本機 Vite 模組回傳 200。瀏覽器沒有部署倉位元件的可見 React 例外，但入口動態模組無法可靠抓取，因此不能把該自動截圖當作產品介面驗收證據，也不能把空白畫面直接歸因於本輪程式修復。[9]

基於交易系統安全，本輪沒有為了截圖而建立、啟用策略或送出真實訂單。最終判定採用共用契約檢查、路由接線審核、唯讀資料庫回讀、決策層數量換算、全量測試、型別檢查與正式建置。待預覽代理工作階段恢復後，可再由使用者以測試帳戶執行一次畫面確認；這不影響目前程式與資料層修復已通過的結論。[9]

## 九、建議的安全人工複核

正式實盤前，建議只在**測試帳戶**選取任一快照值為 100 USDT 的策略，將「實盤部署倉位」改為 500 USDT，建立後確認策略卡片仍顯示 500 USDT；再觸發不送真單的預覽或模擬信號，核對預估下單數量。這是額外的操作層複核，不需要再修改程式。
