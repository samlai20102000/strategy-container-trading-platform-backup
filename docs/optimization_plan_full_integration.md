# 策略容器化自動交易平台：S1/M2/H3 完全集成優化方案

## 1. 概述

本文件旨在提供「策略容器化自動交易平台」S1/M2/H3 三模式部署與回測、快照、策略交易模組的完全集成優化方案。當前系統中，三模式部署工作台功能相對獨立，未能與回測中心、參數快照庫及策略交易模組形成無縫閉環。本方案將詳細闡述如何實現一個統一、高效且軍工級實用的交易系統，確保 S1/M2/H3 模式的配置與執行貫穿整個平台生命週期。

## 2. 目標與願景

實現 S1/M2/H3 三模式部署與回測、快照、策略交易的完全集成，具體目標如下：

1.  **回測中心增強**：允許用戶在回測時選擇策略、S1/M2/H3 部署模式及其他參數，進行模式感知型回測。
2.  **參數快照庫升級**：快照能完整保存並往返 S1/M2/H3 模式相關配置，並可導入至策略交易。
3.  **策略交易模組優化**：新增策略時可直接配置 S1/M2/H3 模式，並與部署工作台無縫銜接。
4.  **部署工作台重構**：將現有部署工作台拆分為「部署管理」與「快速啟動」雙面板，提升操作效率與用戶體驗。
5.  **實盤執行自動化**：實盤執行引擎能自動識別並應用所選部署模式的配置，確保策略行為一致性。
6.  **軍工級 UI/UX**：所有新增與修改的 UI 元素均遵循軍工級專業標準，保持平台整體風格一致性。

## 3. 現有問題分析與痛點

根據用戶反饋與系統現狀，主要痛點如下：

*   **回測中心與部署模式脫節**：回測時無法模擬 S1/M2/H3 模式下的策略行為，導致回測結果與實盤部署預期不符。
*   **部署工作台功能不完善**：部署新稿後未能開始執行，且現有按鈕（如「執行預期推演」、「停用部署」）功能不明或無效。
*   **策略啟動流程不清晰**：用戶不清楚如何在部署工作台中啟動已選策略，或將策略交易中的策略與部署模式關聯。
*   **配置管理碎片化**：S1/M2/H3 模式的配置未能在回測、快照、策略交易和部署之間統一管理和傳遞。
*   **Preflight 與生命週期功能缺失**：點擊策略卡片中的 Preflight 與生命週期僅重定向，未能提供實際的配置或管理功能。
*   **M2/H3 參數配置需求**：用戶希望在 M2/H3 模式下，第二層倉觸發時能設定額外參數，這需要更細粒度的配置控制。

## 4. 完全集成方案詳情

### 4.1 核心架構變革：統一策略配置模式（Unified Strategy Configuration Schema）

為實現完全集成，核心在於建立一個統一的策略配置模式，該模式需包含所有策略參數，並能明確區分 S1/M2/H3 模式下的特有配置。這將是一個巢狀的 JSON Schema，用於前後端數據傳輸、持久化與驗證。

**關鍵點：**

*   **模式感知型配置**：在 `StrategyConfig` 中引入 `deploymentMode: 'S1' | 'M2' | 'H3'` 字段，並根據此字段動態調整其他參數的可用性與預設值。
*   **分層馬丁配置強化**：`layerConfigs` 結構將包含 `multiplier` 和 `stepPct`，並支援無限層級。M2/H3 模式下，可針對特定層級（如第二層倉）定義額外參數，例如：
    ```typescript
    interface MartinLayerConfig {
      layer: number;
      multiplier: number;
      stepPct: number;
      // M2/H3 模式下可選的額外參數
      m2ExtraParam?: number; // 例如：M2模式下第二層倉的額外加倉比例
      h3ProtectionThreshold?: number; // 例如：H3模式下第二層倉的保護門檻
    }
    ```
*   **時間框架統一**：`timeframe` 字段將在所有模組中統一使用，並與交易所支持的時間框架列表進行驗證。

### 4.2 模組優化細節與代碼修改清單

#### 4.2.1 回測中心（Backtest Center）

**UI/UX 建議**：

*   在回測參數設定區塊，新增一個「部署模式」下拉選單或 Tab 頁，提供 S1、M2、H3 選項。
*   當選擇不同模式時，相關參數面板應動態調整，顯示該模式特有的配置項（例如 H3 模式下的保護門檻）。
*   KRM 策略的回測應預設為 30m 時間框架，並支援合法週期選擇。

**代碼修改**：

*   **`client/src/pages/Backtest.tsx`**：
    *   修改回測表單，引入 `deploymentMode` 選擇器。
    *   根據 `deploymentMode` 的值，條件渲染不同的參數輸入組件或調整現有組件的屬性（例如鎖定某些字段）。
    *   更新回測提交邏輯，將 `deploymentMode` 和其相關配置納入回測請求 payload。
*   **`server/services/backtestEngine.ts`**：
    *   修改回測引擎，使其能夠解析 `deploymentMode` 參數。
    *   在策略執行邏輯中，根據 `deploymentMode` 應用不同的規則（例如 M2 模式下的腿級隔離，H3 模式下的保護腿邏輯）。

    *   更新 KRM 策略的 `defaultConfig`，包含 S1/M2/H3 模式的預設值。

**UI/UX 建議**：

*   **`server/services/kamaRainbowMartinAdvancedExecutor.ts`**：

*   **`server/services/deploymentLifecycle.ts`**：
    *   強化部署 preflight 檢查，確保 KRM H3 模式下保護門檻正規化為 4%，避免與通用 H3 預設 5% 衝突。

### 4.3 M2/H3 第二層倉觸發參數澄清與建議

用戶提到「M2和H3即第二層倉觸發可以考慮讓我再設參數」。這通常有兩種解釋：

1.  **動態調整馬丁倍率**：在達到第二層倉時，動態調整該層的 `multiplier` 或後續層級的 `multiplier`。
2.  **層級專屬風控**：在達到第二層倉時，觸發特定的風控邏輯，例如更嚴格的止損、部分平倉或發出警報。

**建議**：

我建議採用 **層級專屬風控** 的方式，因為動態調整倍率會增加策略複雜度且難以回測驗證。層級專屬風控能提供更精確的風險管理能力。這可以在 `MartinLayerConfig` 中增加 `m2ExtraParam` 或 `h3ProtectionThreshold` 等字段來實現，並在實盤執行引擎中根據這些參數觸發相應的邏輯。

### 4.4 軍工級 UI/UX 建議

*   **一致性**：所有新增與修改的 UI 元素必須與現有平台風格保持高度一致，包括顏色、字體、間距、組件樣式（shadcn/ui）。
*   **清晰性**：複雜的配置項應配備清晰的說明文字（tooltip 或 info icon），解釋其作用和影響。
*   **響應式設計**：確保所有頁面在桌面和行動設備上都能良好顯示和操作，特別是分層馬丁表格和部署詳情。
*   **狀態反饋**：操作（如啟動部署、保存快照）應提供即時、明確的視覺反饋（loading 狀態、成功/失敗提示）。
*   **錯誤處理**：所有輸入驗證錯誤應提供友好的錯誤訊息，引導用戶修正。
*   **數據可視化**：部署狀態、Preflight 結果等應以直觀的圖表或徽章形式展示。
